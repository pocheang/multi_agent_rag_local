# 模型温度兼容修复设计

## 目标

修复闲聊请求绕过管理员配置、向当前 `custom/GLM` Provider 发送 `temperature=2.0` 并收到 HTTP 400 的问题，同时把前端全局模型温度限定为 `0–1`。

## 已确认根因

- 全局模型配置已正确保存 `temperature=0.7`。
- `hi` 被识别为闲聊后，`app/agents/synthesizer/generation.py` 使用常量 `2.0` 覆盖保存值。
- 模型运行时优先使用调用方显式温度，因此最终请求没有使用管理员保存的 `0.7`。
- 智谱接口真实返回错误码 `1210`：`temperature` 只允许 `[0,1]`。

## 设计

### 后端

1. 闲聊高温度从 `2.0` 调整为 `0.9`，保留闲聊比默认 `0.7` 更具随机性的语义。
2. 全局模型设置的公开请求 Schema 将温度限制为 `0–1`，新请求超出范围时返回校验错误。
3. 配置归一化将历史或持久化的超范围温度安全收敛到 `0–1`，避免旧数据继续触发 Provider 错误。
4. 模型运行边界针对 `custom` Provider 确保最终温度不超过 `1`，防止内部调用再次绕过设置层校验；不压缩原生支持更大范围的其他 Provider。
5. 不改变 RAGPipeline、查询路由、SSE 事件、Profile 或响应结构。

### 前端

1. 管理员全局模型设置温度滑块和数值状态限定为 `0–1`。
2. 保存和连接测试载荷在客户端边界再次收敛到 `0–1`，避免 DOM 操作或旧状态绕过控件限制。
3. 保留当前步进和显示方式，不做无关 UI 重构。

## 测试与验收

- 后端测试先证明闲聊当前会产生 `2.0`，修复后断言使用 `0.9`。
- 后端测试覆盖全局配置 `0`、`1` 边界和超范围输入。
- 后端测试覆盖 `custom` Provider 运行时最终参数不超过 `1`。
- 前端测试覆盖滑块 `min=0`、`max=1`，以及保存/测试载荷不超过 `1`。
- 运行相关 Pytest、前端 Vitest、前端生产构建和静态检查。
- 重启服务后使用当前 `glm-4.5-flash` 做真实 `temperature=0.9` 探测，并验证一次标准 SSE 查询。

## 非目标

- 不修改 API Key、Base URL、模型名称或用户数据。
- 不修复本任务之外的 Embedding readiness、Redis 认证或非流式 Pipeline 缺陷。
