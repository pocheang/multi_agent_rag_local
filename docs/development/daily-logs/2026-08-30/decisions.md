# 2026-08-30 技术决策 / Decisions

## 基准跑批应该用哪个语料库？(Which corpus should the benchmark measure?)

**决策**：用发起请求的管理员的真实身份跑，不额外收窄范围。

给基准跑批补上身份之后，检索范围就受访问控制约束了。对一个 `role=admin` 的调用者，
`app/services/security/access_scope.py::list_visible_document_rows` 返回：

- 共享语料 `data/docs/` 下的全部文档（对任何已认证用户都可见）
- 该管理员自己上传的文档
- `visibility=public` 的文档
- 同租户的文档（注意：`tenant_id` 未显式传入时回落为 `user_id`，实际上这一条很少命中）

**后果，必须知道**：一次基准跑批衡量的是"这位管理员能看到的语料"，不是一个固定语料库。
两位可见文档不同的管理员跑出来的趋势不能直接对比。`GET /admin/ops/benchmark/trends`
的历史记录里没有记录跑批者身份，所以这一点只能靠本文档约束。

**被否决的方案**：把范围强制收窄到共享的 `data/docs/`。

- 它衡量的是产品里根本不存在的一条路径——真实用户查询永远带着自己的可见范围。
- 实现上需要合成一个假 actor 或绕开 resolver，而 resolver 的 fail-closed 正是
  2026-08-30 用户数据隔离工作要建立的东西，为了跑批在它上面开个口子不划算。

**如果以后确实需要可对比的固定基线**：正确做法是建一个专用的基准用户，把基准语料
以该用户所有者身份入库，然后以那个身份跑批——而不是让跑批路径绕过访问控制。
