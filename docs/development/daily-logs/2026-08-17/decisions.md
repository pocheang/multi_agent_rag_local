# 技术决策记录

## 决策1: 选择选项B架构（增强Router合一）

**日期**: 2026-08-17

**背景**:
有两个架构选项：
- 选项A: 新Router（澄清） → 旧Router（分类） → Planner
- 选项B: 增强Router（澄清+分类合一） → Planner

**决策**: 选择选项B

**理由**:
1. **减少网络往返**: 一次调用完成澄清判断和路由分类
2. **简化状态管理**: 不需要在两个Router之间传递状态
3. **降低延迟**: 避免两次LLM调用
4. **代码内聚性**: 澄清逻辑和路由逻辑紧密相关，放在一起更合理
5. **易于测试**: 单一服务更容易编写集成测试

**代价**:
- EnhancedRouterService代码量增加
- 需要重构现有RouterAgentService（但保持兼容）

**缓解措施**:
- 使用组合模式，EnhancedRouterService内部调用RouterAgentService
- 保持现有RouterAgentService不变，作为fallback

## 决策2: 澄清上下文存储在会话历史中

**日期**: 2026-08-17

**背景**:
澄清上下文可以存储在：
1. 会话历史文件（session.json）
2. 独立的Redis缓存
3. 数据库表

**决策**: 存储在会话历史文件

**理由**:
1. **一致性**: 会话相关的所有状态都在一个地方
2. **持久化**: 自动随会话保存，不需要额外的过期策略
3. **简单性**: 不需要引入新的存储依赖
4. **可追溯**: 可以看到历史澄清记录
5. **已有基础设施**: HistoryStore已经支持JSON存储

**代价**:
- 会话文件略微增大（约100-500字节）
- 需要修改HistoryStore

**缓解措施**:
- 澄清完成后重置上下文，避免累积
- 使用紧凑的JSON格式

## 决策3: 动态轮次（2-10轮，根据意图复杂度自适应）

**日期**: 2026-08-17（已更新）

**背景**:
需要确定澄清轮次的上限。不同意图的复杂度差异很大，固定轮次不够灵活。

**决策**: 动态轮次，根据意图复杂度自动确定（2-10轮）

**轮次分配策略**:
| 意图类型 | 复杂度 | 最大轮次 | 典型问题 |
|---------|--------|----------|----------|
| simple_query | 简单 | 2轮 | "价格是多少？" |
| document_lookup | 简单 | 3轮 | "查找某个文档" |
| document_comparison | 中等 | 5轮 | "对比两个产品" |
| rag_design | 复杂 | 7轮 | "设计RAG系统" |
| system_architecture | 复杂 | 8轮 | "设计微服务架构" |
| complex_analysis | 极复杂 | 10轮 | "多维度数据分析" |
| default | 默认 | 5轮 | 未知意图 |

**理由**:
1. **灵活性**: 简单问题快速完成（2-3轮），复杂问题充分澄清（7-10轮）
2. **用户体验**: 避免简单问题过度询问，复杂问题信息不足
3. **成本优化**: 按需分配轮次，不浪费
4. **可扩展**: 易于添加新的意图类型和轮次配置

**实现细节**:
```python
# 识别意图后动态设置max_rounds
intent = await self._identify_intent(question)
context.max_rounds = self._get_max_rounds_for_intent(intent)
```

**代价**:
- 需要维护意图→轮次的映射配置
- 意图识别错误会影响轮次分配

**缓解措施**:
- 设置合理的默认值（5轮）
- 提供配置文件支持动态调整
- 记录实际使用轮次，持续优化配置
- 超过最大轮次后，使用已收集信息继续执行

## 决策4: 前端使用模态覆盖而非内联澄清

**日期**: 2026-08-17

**背景**:
澄清UI可以设计为：
1. 模态覆盖（替换整个聊天区域）
2. 内联插入（在消息流中插入澄清卡片）
3. 侧边栏（在右侧显示澄清面板）

**决策**: 模态覆盖

**理由**:
1. **聚焦**: 用户注意力集中在澄清问题上
2. **避免混淆**: 不会与历史消息混在一起
3. **易于实现**: 状态管理简单，显示/隐藏即可
4. **移动端友好**: 小屏幕上体验更好
5. **参考案例**: 类似Siri、Google Assistant的澄清界面

**代价**:
- 用户无法同时看到历史消息（但已收集信息会显示）
- 切换体验略显突兀

**缓解措施**:
- 在澄清界面显示"已收集信息"摘要
- 提供"取消"按钮，允许用户返回
- 显示进度（第X/5轮）

## 决策5: 从历史消息智能提取信息（保守策略）

**日期**: 2026-08-17

**背景**:
历史消息中可能包含有用信息，可以：
1. 不提取，每次都询问
2. 规则提取（正则匹配）
3. LLM提取（调用模型）

**决策**: 规则提取（保守策略）

**理由**:
1. **性能**: 无需额外LLM调用
2. **可控**: 提取逻辑明确，便于调试
3. **准确性**: 规则匹配不会产生幻觉
4. **增量**: 未来可以升级为LLM提取

**代价**:
- 提取能力有限，只能识别明显的关键词
- 需要维护提取规则

**缓解措施**:
- 用户可以修正提取的信息（选择不同选项或自定义输入）
- 记录提取日志，持续优化规则
- Phase 2 可以引入LLM辅助提取

## 决策6: 独立API路由 `/api/v1/clarification/check`

**日期**: 2026-08-17

**背景**:
澄清逻辑可以：
1. 集成到现有的 `/query` 路由
2. 独立为新路由 `/api/v1/clarification/check`

**决策**: 独立新路由

**理由**:
1. **向后兼容**: 不影响现有查询流程
2. **职责分离**: 澄清检查和查询执行是两个阶段
3. **灵活性**: 前端可以先检查，再决定是否查询
4. **测试性**: 独立路由更容易测试
5. **渐进迁移**: 可以逐步推广，不破坏现有功能

**代价**:
- 多一次网络请求（check → query）

**缓解措施**:
- check接口轻量，延迟<100ms
- 未来可以考虑合并为一个streaming接口

## 决策7: 选项 + 自定义输入的混合模式

**日期**: 2026-08-17

**背景**:
用户回答可以设计为：
1. 纯选项（单选/多选）
2. 纯自由输入
3. 混合模式（选项 + 允许自定义）

**决策**: 混合模式

**理由**:
1. **平衡**: 常见场景用选项（快速），特殊场景用自定义（灵活）
2. **降低门槛**: 选项降低用户思考成本
3. **不限制**: 自定义输入保证任何情况都能表达
4. **参考案例**: 大多数表单设计都采用"其他（请说明）"模式

**代价**:
- UI略复杂

**缓解措施**:
- 默认显示选项，"自定义输入"作为次要入口
- 切换体验流畅（动画过渡）

## 决策8: 意图识别配置化（JSON配置文件）

**日期**: 2026-08-17

**背景**:
意图和所需信息的映射可以：
1. 硬编码在代码中
2. 存储在配置文件（JSON/YAML）
3. 存储在数据库
4. 使用LLM动态生成

**决策**: 硬编码在代码中（Phase 1），配置文件（Phase 2）

**理由**:
1. **快速迭代**: Phase 1 先验证可行性
2. **类型安全**: Python代码有类型提示
3. **性能**: 无需读取文件或查询数据库
4. **未来扩展**: 重构为配置文件很容易

**Phase 2计划**:
- 将 `INTENT_REQUIRED_INFO` 移到 `config/clarification_intents.json`
- 支持热重载
- 支持用户自定义意图

## 决策9: 澄清完成后重置上下文

**日期**: 2026-08-17

**背景**:
澄清上下文可以：
1. 保留到会话结束
2. 澄清完成后立即重置
3. 保留X分钟后过期

**决策**: 澄清完成后立即重置

**理由**:
1. **避免混淆**: 下一个问题不应该继承上一个问题的澄清信息
2. **节省空间**: 减少会话文件大小
3. **语义清晰**: 每个问题独立处理

**代价**:
- 用户连续提问相同意图时，需要重新澄清

**缓解措施**:
- 从历史消息提取信息时，考虑最近几轮对话
- 未来可以引入"会话主题"概念，保留主题相关的上下文

## 决策10: 错误降级策略

**日期**: 2026-08-17

**背景**:
当澄清逻辑出错时，可以：
1. 返回错误给用户
2. 降级为直接执行查询
3. 使用默认值继续澄清

**决策**: 降级为直接执行查询

**理由**:
1. **可用性**: 澄清是增强功能，不应成为障碍
2. **用户体验**: 用户提问后总应该得到答案
3. **渐进增强**: 澄清失败不影响核心功能

**实现**:
```python
try:
    decision = await enhanced_router.route(request, context)
except Exception as e:
    logger.warning(f"Clarification failed: {e}")
    # 降级为基础Router
    base_decision = await base_router.route(request)
    decision = EnhancedRouteDecision(
        ...base_decision,
        action=RouterAction.CONTINUE
    )
```

## 技术栈选择总结

| 组件 | 技术选择 | 理由 |
|------|----------|------|
| 状态管理 | 会话历史文件 | 持久化、一致性 |
| 前端UI | React状态 + 模态 | 简单、聚焦 |
| 后端架构 | 增强Router合一 | 减少调用、内聚 |
| 信息提取 | 规则匹配 | 性能、可控 |
| 配置管理 | 代码硬编码 → JSON | 渐进演进 |
| 错误处理 | 降级策略 | 可用性优先 |
