## 🎯 问题

**位置**: [app/agents/rag/service.py:339-340](../app/agents/rag/service.py#L339-L340)

错误消息截断过于激进，200字符限制可能丢失关键调试信息：

```python
# ❌ 旧代码 - 200字符太短
error_msg = str(result)
if len(error_msg) > 200:
    error_msg = error_msg[:200] + "..."
```

### 问题分析

1. **信息丢失**: 
   - 200字符对于复杂错误消息太短
   - 可能截断关键的堆栈跟踪或参数信息
   - 难以诊断生产环境问题

2. **调试困难**:
   - 错误消息被截断后无法看到完整上下文
   - 需要额外的日志配置才能获取完整信息

3. **不一致的体验**:
   - 有些错误被完整记录，有些被严重截断
   - 开发者不知道哪些信息被丢失了

---

## 🔧 解决方案

增加限制到1000字符，并添加配置常量：

```python
# ✅ 新代码 - 1000字符 + 命名常量
# 模块级常量
ERROR_MESSAGE_MAX_LENGTH = 1000

# 使用常量
error_msg = str(result)
if len(error_msg) > ERROR_MESSAGE_MAX_LENGTH:
    error_msg = error_msg[:ERROR_MESSAGE_MAX_LENGTH] + "... (truncated)"
```

### 改进点

1. ✅ **5倍长度**: 200字符 → 1000字符
2. ✅ **命名常量**: `ERROR_MESSAGE_MAX_LENGTH`（易于调整）
3. ✅ **清晰标记**: `"... (truncated)"` 明确表示被截断
4. ✅ **更好的注释**: 说明完整错误仍在traceback中

### 实际影响

**典型错误消息长度**:
- 简单错误: ~50-100字符 ✅（完整显示）
- 中等错误: ~200-500字符 ✅（完整显示）
- 复杂错误: ~500-2000字符 ⚠️（部分截断，但保留关键信息）
- 极长错误: >2000字符 ⚠️（截断，但1000字符通常足够）

## 📝 设计考虑

### 为什么1000字符？

**平衡考虑**:
1. ✅ **足够的上下文**: 大多数错误消息 <1000字符
2. ✅ **防止日志爆炸**: 避免单条消息几MB
3. ✅ **可读性**: 1000字符在终端中仍然可读
4. ✅ **性能**: 字符串操作开销可接受

**如果需要更多**:
- 完整的异常traceback仍然可用
- 可以通过日志配置查看完整错误
- 可以调整常量 `ERROR_MESSAGE_MAX_LENGTH`

### 为什么不完全移除限制？

**保留限制的原因**:
1. ❌ **日志爆炸**: 某些错误可能包含大量数据
2. ❌ **性能问题**: 极长字符串影响日志系统
3. ❌ **可读性**: 过长的消息难以阅读
4. ❌ **存储成本**: 日志存储成本增加

## 🎓 最佳实践

### 错误消息截断策略

**好的截断**:
```python
# ✅ 使用命名常量
MAX_ERROR_LENGTH = 1000
if len(msg) > MAX_ERROR_LENGTH:
    msg = msg[:MAX_ERROR_LENGTH] + "... (truncated)"
```

**差的截断**:
```python
# ❌ 硬编码，无标记
if len(msg) > 200:
    msg = msg[:200]
```

### 何时截断？

**应该截断**:
- 用户界面显示（UI空间有限）
- 事件报告（避免事件系统过载）
- 短信/通知（字符限制）

**不应该截断**:
- 日志文件（配置日志系统限制）
- 调试输出（完整信息优先）
- 错误追踪系统（需要完整堆栈）
